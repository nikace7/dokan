# Nepali Localization — BS calendar, money, and language

The conventions that make Dokan Nepali-native. Sources of truth: backend
`backend/core/calendar/bs.py` and `backend/core/money.py`; frontend
`frontend/src/lib/bs/` and `frontend/src/lib/money.ts`. The authoritative
specification is `docs/SYSTEM_DESIGN.md` §6–§7; where this doc and the code
disagree, the code is right.

---

## 1. The one rule that governs everything

**The API and the database speak AD. BS is a presentation and reporting
concern.**

- API requests and responses exchange **AD ISO strings** (`2025-07-27`).
  Never send or store a BS date as the only value — conversion tables change;
  AD is the anchor.
- BS conversion exists in exactly **two** places:
  - Backend: `core/calendar/bs.py` (wraps `nepali-datetime`). Grepping the
    backend for `nepali_datetime` outside this module (and its tests/fixture
    generator) must return nothing.
  - Frontend: `frontend/src/lib/bs/` (the only module allowed to import
    `nepali-date-converter`).
- Both sides must pin conversion tables that agree. The backend pins
  `nepali-datetime>=1.0.7`; the frontend `nepali-date-converter` 3.x.

---

## 2. Denormalized BS columns on every transaction row

BS reporting is fast because conversion never happens in SQL. At write time,
services denormalize the business-date triplet onto every transaction row
(`stock_movement`, sales invoices and returns, payments, purchase invoices,
expenses — see `apps/inventory/services.py::_business_dates` for the
pattern):

| Column | Type | Format | Why |
|---|---|---|---|
| `business_date_ad` | `date` | AD operating date in `Asia/Kathmandu` | Single source of truth |
| `business_date_bs` | `char(10)` | Zero-padded `'2082-04-12'` | Lexicographically sortable, `BETWEEN`-comparable, directly indexable |
| `fiscal_year_bs` | `char(7)` | `'2082-83'` | Nepali fiscal year grouping and invoice numbering |

With these columns, every BS report is a plain indexed range scan
(`WHERE business_date_bs BETWEEN …`) or a `GROUP BY fiscal_year_bs` — no
conversion function in the query path. Reports group BS months by **string
prefix** on these columns; the only date arithmetic in `apps/reports` is a
month-boundary helper (`selectors/_dates.py`) that looks up month length
through the conversion table once per request. Report endpoints accept BS
parameters (e.g. a `'YYYY-MM'` BS month) and validate/convert at the
boundary.

## 3. Conversion contract

Backend (`core/calendar/bs.py`):

| Function | Behaviour |
|---|---|
| `ad_to_bs(d: date) -> str` | AD → zero-padded BS string `'YYYY-MM-DD'` |
| `bs_to_ad(bs: str) -> date` | Strict: malformed input raises `ValueError`, not a guess |
| `fiscal_year_bs(d: date) -> str` | `'2082-83'` — see §4 |
| `today_bs() -> str` | Today in `Asia/Kathmandu`, as BS |

Frontend (`src/lib/bs/index.ts`) mirrors this: `adToBs`, `bsToAd`,
`toBsString`, `formatBs`, `fiscalYearBs`, plus `toDevanagariDigits`.

**Out-of-range input is an error, never a silent wrong date.** The backend
table covers BS 1975-01-01 .. 2100-12-30 (AD 1918 .. 2044) and raises
`OutOfRangeError` outside it. The frontend's installed library covers the
narrower BS 2000-01-01 .. 2090-12-30 (AD 1943-04-14 .. 2034-04-13) and
explicitly guards the AD side too, because the library silently wraps
out-of-range AD dates into wrong BS dates instead of throwing. The narrower
frontend range is the effective limit until a wider table is adopted on both
sides.

**Golden fixture.** `backend/core/tests/fixtures/bs_golden.json` holds ~500
known AD↔BS pairs (generated by `backend/scripts/generate_bs_golden.py`,
asserted in `core/tests/test_bs_calendar.py`). This is the test that catches
a library upgrade silently breaking dates. The design calls for the frontend
to run the same fixture; that sharing lands with the first date-dependent
frontend feature.

## 4. The Nepali fiscal year

The fiscal year runs **Shrawan 1 (BS month 04) → Ashad end (BS month 03 of
the following BS year)**, formatted `char(7)` as `'2082-83'`. Both
implementations agree: `start_year = bs.year if bs.month >= 4 else
bs.year - 1`, end suffix is the last two digits of `start_year + 1`.

`fiscal_year_bs` is not cosmetic: gapless invoice numbering sequences are per
(tenant, branch, doc_type, fiscal_year_bs) — the counter resets with the
Nepali year, as IRD expects.

## 5. Business day boundary

A sale rung at 23:40 belongs to "today" by the shopkeeper's reckoning.
`tenant_setting.day_start_time` (default `'00:00'`, typical shops set
`'04:00'`) shifts the operating date:

```
business_date_ad = (datetime_ad AT TIME ZONE 'Asia/Kathmandu' - day_start_time).date()
```

Set once at onboarding; changing it later does not rewrite history — an audit
note records the change. (SYSTEM_DESIGN §6.2)

---

## 6. Timezone and currency

- Timezone is **`Asia/Kathmandu`** everywhere: `business_date_ad` is derived
  in it, `today_bs()` reads the clock in it. `created_at`-style timestamps
  are stored as `timestamptz` (UTC) — the single source of truth.
- Currency is **NPR only** (`CURRENCY_NPR = "NPR"`). There is no
  multi-currency path and none is planned for Phase 1.

## 7. Money: Decimal backend, integer paisa frontend

Two implementations of the same display conventions:

| | Backend `core/money.py` | Frontend `src/lib/money.ts` |
|---|---|---|
| Representation | `Decimal` — `quantize_money` rounds to 2 places `ROUND_HALF_UP` and **refuses floats** | Integer **paisa** (`Paisa`, 1 rupee = 100 paisa); floats only at input boundaries via string parsing, never `x * 100` |
| Grouping | Lakh/crore: `1,23,456.00` — last 3 digits, then pairs | Same (`groupIndianStyle`) |
| Symbol | `Rs` prefix (`format_npr`) | `रू ` prefix (`formatNpr`) |
| Devanagari | `numerals="devanagari"` → `१,२३,४५६.००` | `devanagari: true` option |

**Artifact rule (one symbol per artifact, chosen per channel):** on-screen UI
and the printed 80mm receipt use `रू` (frontend-rendered); SMS receipts use
the ASCII `NPR` prefix (`apps/notifications/templates.py`) because a
non-GSM-7 `रू` forces UCS-2 encoding and doubles the segment count. Backend
`format_npr` (`Rs`) currently has no production callers — anything that
adopts it must follow the same per-channel rule, and no single artifact may
ever mix two symbols.

Examples:

```
format_npr(Decimal("123456"))                    → 'Rs 1,23,456.00'
format_npr(Decimal("123456"), numerals="devanagari") → 'Rs १,२३,४५६.००'
formatNpr("123456")                              → 'रू 1,23,456.00'
```

Never use Western thousands grouping (`123,456`) anywhere user-facing, and
never do float money arithmetic on either side.

## 8. Bilingual UI conventions

The UI is bilingual **Nepali + English**, with Nepali labels on
counter-facing screens (AGENTS.md, SYSTEM_DESIGN §6.4, §7):

- **Labels**: Nepali + English side by side initially, then per-user
  preference. No jargon — "Stock" not "Inventory Ledger", "Baki" not
  "Accounts Receivable". Errors say what to *do*.
- **Calendar preference** (`tenant.calendar_pref`): `BS` (default) / `AD` /
  `BOTH`; in `BOTH`, BS is primary and AD shows as small grey secondary text.
- **Numerals**: Devanagari (`२०८२`) or Arabic (`2082`) per user preference;
  Devanagari is the default for `locale=np`. Both `formatBs` and the money
  formatters already take a Devanagari option.
- **Receipts** print BS prominently and AD in small text (some B2B customers
  need AD). The landed 80mm receipt is bilingual.
- **Month names**: बैशाख, जेठ, असार, साउन, भदौ, असोज, कार्तिक, मंसिर, पुष,
  माघ, फागुन, चैत. BS months run 29–32 days — a generic 30/31-day picker is
  wrong.

The i18n framework itself is deliberately **not built yet**
(`frontend/src/lib/i18n/README.md`): the string count is small and counter
screens are fixed, so a tiny typed message map will likely be enough. Do not
scaffold one before a real screen needs translated strings. What exists today
is the display layer: Devanagari numerals for money and BS dates.
